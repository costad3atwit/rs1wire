\section{Introduction}

The 1-Wire protocol, developed by Maxim Integrated (now Analog Devices), connects multiple devices over a single data line \cite{Analog_Devices_1w}, which makes it well suited to applications where space and wiring are limited.
One of the most popular 1-Wire devices is the DS18B20 digital temperature sensor \cite{ds18b20_datasheet}, widely used in hobbyist and laboratory settings, particularly with single-board computers (SBCs) such as the Raspberry Pi and BeagleBone.
On these boards, Linux provides a 1-Wire subsystem: the `w1-gpio` bus master drives the bus, and the `w1\_therm` slave driver exposes each sensor's readings, in millidegrees Celsius, as sysfs files under `/sys/bus/w1/devices/` \cite{kernel_w1_therm_docs}.
At the same time, Rust is gaining traction in embedded and systems programming for its memory safety and efficient runtime \cite{sharma2024rust}.
Yet no maintained Rust library makes full use of the kernel's 1-Wire interface, and this work aims to fill that gap in both existing software and the literature.

\subsection{Problem}

\textbf{Rust users on Linux SBCs}

Current Rust 1-Wire crates focus almost entirely on implementing the protocol in userspace using bit-banging and the widely utilized embedded-hal crate \cite{fuchsnj_one_wire_bus, fuchsnj_ds18b20}. 
This is because many Rust users are embedded developers who work on bare-metal microcontrollers \cite{state_of_rust_embedded_2026} without an operating system. 
This method is unsuitable for Linux developers because userspace bit-banging is exposed to scheduler preemption and jitter, which can corrupt the timing-sensitive 1-Wire protocol \cite{adam2021performance}. 
The only Rust crate that reads kernel output, `w1\_therm\_reader`, is a small single-sensor parser that its author describes as incomplete: ``If you want a complete OneWire library, this crate is not the one you're looking for'' \cite{w1_therm_reader}.
It lacks features such as device discovery, bulk reading, and configuration, which this project aims to provide.
It also panics on malformed input, which is not ideal for robust applications.

\textbf{Python users}

While Rust is in itself a systems programming language and can be used with an operating system, when one is present (e.g., Linux), Python is often the language of choice for hobbyist and experimental userspace applications. 
As such there are several Python libraries available for interacting with 1-Wire devices via the Linux sysfs interface. 
The de facto standard Python library packaged with Raspberry Pi OS, `w1thermsensor`, reads sensors one at a time in released versions \cite{w1thermsensor}. 
This results in a cost of approximately 750 ms (12-bit conversion) per sensor \cite{ds18b20_datasheet}, so N sensors cost approximately N conversion times. 
This notably ignores the update to the linux kernel which supports bulk reading \cite{kernel_w1_therm_docs}. 
Users have requested bulk read functionality (w1thermsensor issue \#115), and PR \#120 implements it but remains unmerged \cite{w1thermsensor_pr120}. 
Other less prolific Python modules do utilize this kernel feature, but none of them prevent stale reads, which can return trigger-time values hours later with no expiry \cite{kernel_w1_therm_abi}. 
This is a hazard for monitoring and control loops, as it can result in silent stale or wrong values, which are worse than errors. 
The existing bulk consumers (w1-therm-api \cite{w1_therm_api}, wb-mqtt-w1 \cite{wb_mqtt_w1}) do not prevent this at the API level. 
This is a significant gap because multi-sensor setups are the main draw of the 1-Wire protocol, and they scale linearly in read latency under sequential reads. 
Additionally, generic failure values (w1-therm-api returns `None` for every failure) hide the cause of the failure, making it difficult to diagnose issues such as wiring problems, CRC errors, power-on resets, or missing drivers.

\section{Background}\label{sec:background}

\subsection{1-Wire protocol}

The 1-wire protocol is a simple, low-cost, single-master, multi-slave communication system that can use a single data line for both power and data transmission \cite{Analog_Devices_1w}.
Devices can be powered externally (approach used in this work) or by parasite power from the data line.
The master initiates all communication on the bus and controls the timing of all transactions.
A transaction begins with a reset pulse from the master, followed by a presence pulse from the slave(s).
Bits are sent in time slots on the order of tens of microseconds, with the master and slaves sampling at fixed offsets meaning that timing errors can easily corrupt bits.
Each 1-Wire device has a unique 64-bit Read Only Memory (ROM) ID comprised of an 8 bit family code, a 48-bit serial number, and an 8-bit CRC \cite{Analog_Devices_1w}.
Software (bit-banged) masters are common, but the precise timing of the protocol is difficult to perform correctly in spaces where the software isn't in total control of the hardware \cite{Analog_Devices_1w_software}.
\subsection{DS18B20}

\begin{figure}[htbp]
  \centering
  \includegraphics[width=0.6\columnwidth]{ds18b20_img.jpg}
  \caption{DS18B20 waterproof probe. Image from \cite{voltaat_ds18b20}.}
  \label{fig:ds18b20}
\end{figure}

\begin{itemize}
\item Family code `0x28` \cite{ds18b20_datasheet}
\item Range -55 to +125 C; +/-0.5 C accuracy from -10 to +85 C \cite{ds18b20_datasheet}
\item Configurable resolution 9-12 bits; max conversion time 93.75 / 187.5 / 375 / 750 ms \cite{ds18b20_datasheet}
\item Convert T command starts conversion; result read from 9-byte scratchpad \cite{ds18b20_datasheet}
\item Scratchpad byte 8 is Dallas/Maxim CRC-8 over bytes 0-7 (polynomial $x^8 + x^5 + x^4 + 1$) \cite{ds18b20_datasheet}
\item Power-on reset value of the temperature register is +85 C \cite{ds18b20_datasheet}; indistinguishable from a genuine 85 C reading
\item Resolution lives in scratchpad RAM (lost on power off unless copied to EEPROM) \cite{ds18b20_datasheet}
\item Convert T can be addressed to all devices at once (Skip ROM), which is what makes bulk conversion possible \cite{ds18b20_datasheet}
\end{itemize}

\subsection{Linux w1 subsystem}

\begin{itemize}
\item `w1-gpio`: bus master driver that bit-bangs a GPIO pin from kernel space
  \begin{itemize}
  \item Enabled on Raspberry Pi via `dtoverlay=w1-gpio` in `/boot/firmware/config.txt` (default GPIO4; `gpiopin=` to change) `[VERIFY + cite RPi config docs]`
  \end{itemize}
\item `w1\_therm`: slave driver for temperature sensors \cite{kernel_w1_therm_docs}
\item sysfs layout:
  \begin{itemize}
  \item `/sys/bus/w1/devices/w1\_bus\_masterN/` with `w1\_master\_slaves`, `w1\_master\_slave\_count`, `w1\_master\_search`, `therm\_bulk\_read`
  \item `/sys/bus/w1/devices/28-xxxxxxxxxxxx/` (symlink into its bus master) with `w1\_slave`, `temperature`, `resolution`, `conv\_time`, others \cite{kernel_w1_therm_abi}
  \end{itemize}
\item `w1\_slave` format (two lines):
  \begin{itemize}
  \item Line 1: 9 scratchpad bytes, `: crc=XX YES\textbar{}NO` \cite{kernel_w1_therm_docs}
  \item Line 2: bytes of the last scratchpad that passed CRC (not necessarily the current one), then `t=\textless{}millidegrees C\textgreater{}`
  \end{itemize}
\item Reading `w1\_slave` or `temperature` with no pending bulk result triggers a single-sensor conversion and blocks ~conv\_time \cite{kernel_w1_therm_abi}
\item `therm\_bulk\_read` (per bus master):
  \begin{itemize}
  \item Write `trigger`: Convert T to all sensors on the bus \cite{kernel_w1_therm_docs}
  \item Write is synchronous: kernel sleeps for the longest `conv\_time` on the bus before returning (from `w1\_therm.c`, rpi-6.18.y) `[VERIFY line refs]`
  \item Read: `-1` conversion in progress, `1` complete with unread results, `0` nothing pending \cite{kernel_w1_therm_docs, kernel_w1_therm_abi}
  \item Default permissions 0644 root: unprivileged users cannot trigger
  \end{itemize}
\item Stale-read mechanism (kernel source, rpi-6.18.y):
  \begin{itemize}
  \item Each sensor has a pending-result flag set by the bulk trigger
  \item `w1\_slave\_show` / `temperature\_show`: if flag is 1, read scratchpad and clear it; if 0, call `convert\_t()` (fresh conversion)
  \item No expiry: a result read hours later is still the trigger-time value
  \item Consequence 1: late read returns stale data silently \cite{kernel_w1_therm_abi}
  \item Consequence 2: second read of same sensor silently costs a new full conversion
  \end{itemize}
\item Read failures: kernel returns an empty file rather than an error code
\item Bus mutex (rpi-6.18.y): without strong pull-up (externally powered), held through the conversion sleep, so concurrent per-sensor conversions on one bus serialize; with strong pull-up it is released before sleeping `[VERIFY on hardware: async vs. sequential timing]`
  \begin{itemize}
  \item Implication: threads/asyncio cannot recover the bulk advantage on a single externally powered bus
  \end{itemize}
\end{itemize}

\subsection{Userspace timing on Linux (why not bit-bang in userspace)}

\begin{itemize}
\item Userspace worst-case GPIO latency ~147-160 us vs. kernel-space ~67-76 us on Pi 3 / BeagleBone \cite{adam2021performance} `[VERIFY figures]`
\item PREEMPT\_RT brings jitter below ~50 us \cite{adam2021real}
\item Even RT Linux shows tens of us jitter; sub-us needs interrupt isolation \cite{zhou2025towards} (preprint)

\section{Methodology}

% Design and harness are implemented, so these bullets reflect the current code. Hardware figures already placed in rs1wire.tex.

\subsection{Design goals}

The rs1wire library is designed to consume only kernel-produced results so as to avoid implementing 1-Wire timing in userspace and inheriting the associated latency and jitter issues.
It also makes stale bulk reads impossible to do by accident via runtime checks and type system enforcement.
It supports user's understanding of potential issues with one error variant per failure case and by never panicking on kernel output.

\subsection{API structure (Rust)}

The public API mirrors the sysfs hierarchy in three handle types, and every fallible call returns a typed `Error` rather than a sentinel value.
The entry point, `W1`, holds only the sysfs root path.
It defaults to `/sys/bus/w1/devices`, but `W1::with\_root()` accepts any directory, so tests can run against fixture trees instead of hardware.
From it, `bus\_masters()` and `bus(name)` return bus handles, and `sensors()` and `sensor(id)` find DS18B20s across all buses.
A missing root, or one with no bus masters, is reported as the `w1-gpio` module not being loaded.

A `BusMaster` discovers its sensors from the kernel's `w1\_master\_slaves` list, keeping only family `0x28`.
It also owns the bulk path: `bulk\_status()` maps the `therm\_bulk\_read` values `-1`, `1`, and `0` to an enum, and `bulk\_convert()` writes `trigger` and returns a `BulkConversion` handle (Section~\ref{sec:stale}).
`discard\_pending()` clears results left behind by another process.

A `Sensor` performs individual reads through `read()`, or `read\_with()` to change the 85~$^\circ$C policy, and refuses to read while a bulk result is pending.
It also gets and sets `resolution` and `conv\_time`.
These writes require root, and the resolution lives in sensor RAM, since saving it to EEPROM is not supported; changing it also resets any `conv\_time` override.

The value types encode the kernel's rules so that invalid input cannot be expressed.
`DeviceId` is parsed strictly from the kernel's `28-xxxxxxxxxxxx` name, and `Temperature` stores integer millidegrees exactly as reported, with no floating-point rounding until the caller asks for degrees.
`Resolution` is a four-variant enum covering 9 to 12 bits.
`ConvTime` is `DEFAULT`, `MEASURE` (the kernel times a real conversion), or a fixed number of milliseconds of at least 2, since the kernel reserves 0 and 1 for the first two.

\subsection{Stale-read prevention (core contribution; candidate figure: state diagram)}\label{sec:stale}

The kernel's bulk-read interface leaves freshness entirely to the caller.
After a `trigger`, each sensor holds a pending result that is returned by its next read, whenever that read happens, and is then cleared \cite{kernel_w1_therm_abi}.
Two hazards follow.
A read made long after the trigger silently returns the trigger-time value, and a second read of the same sensor silently starts a fresh single-sensor conversion, costing a full conversion time. rs1wire addresses both by tying every bulk result to the one conversion that produced it.
`bulk\_convert()` does not return temperatures directly; it returns a `BulkConversion` handle, and the only way to obtain a bulk result is through that handle.
Fig.~\ref{fig:bulk_sensor} traces one sensor's result through that handle, and Fig.~\ref{fig:bulk_bus} shows the bus-wide status the kernel reports alongside it.

\begin{figure}[htbp]
  \centering
  \subfloat[Per-sensor states within one `BulkConversion` handle]{\includegraphics[width=\columnwidth]{statediagram_panelA}\label{fig:bulk_sensor}}
  \\
  \subfloat[Bus status reported by `therm\_bulk\_read`]{\includegraphics[width=\columnwidth]{statediagram_panelB}\label{fig:bulk_bus}}
  \caption{Bulk-read state machines. Refusals in (a) are enforced per handle within one process.}
  \label{fig:bulk_states}
\end{figure}

Wherever possible, the handle's guarantees are enforced at compile time.
The `BulkConversion` mutably borrows its `BusMaster`, so Rust's borrow checker allows at most one live conversion per bus handle, and a new trigger cannot be issued on that handle while results from the previous one are still outstanding.
`read\_all()` takes the handle by value, consuming it, so reading the whole conversion twice is a compile error rather than a runtime bug; a `compile\_fail` doctest checks that this code is rejected.

The remaining hazards depend on which sensor is requested and on elapsed time, so they cannot be expressed in types and are instead checked at runtime when `read(id)` is called.
Each refusal is an `Error::StaleBulkRead` carrying a `StaleReason` that names the specific hazard.
`AlreadyRead` rejects a second read of a sensor, which the kernel would otherwise serve with a new conversion.
`Expired` rejects any read made later than `max\_age` after the conversion completed.
Because the kernel has no expiry of its own, this window is a policy of the crate rather than a physical limit; it defaults to 1~s and is measured from the moment the `trigger` write returns, which is when the kernel marks results ready.
`NotInConversion` rejects a sensor that was not on the bus when the conversion began, using the sensor list taken from `w1\_master\_slaves` just before the trigger.

Results that are never requested also need handling, because the kernel would otherwise keep them and hand them to some later, unrelated read.
When a `BulkConversion` is dropped, it reads and discards every result it did not hand out, at roughly 10--15~ms per sensor; sensors refused as `Expired` stay on this list, so their stale values are cleared as well.
The same concern applies to individual reads made outside any handle.
`Sensor::read()` first checks the bus's `therm\_bulk\_read` status and refuses with `BulkPending` if unread bulk results exist, since the kernel would return them in place of a new conversion.
Results left by another process can be cleared with `BusMaster::discard\_pending()`.
Likewise, `bulk\_convert()` refuses with `ConversionInProgress` if a conversion is already running on the bus.

These guarantees are complete only within a single process.
The status checks read `therm\_bulk\_read` and then act on it, so another process that triggers a conversion between the check and the read can still cause a stale or unexpected result.
This race is a limitation of the sysfs interface, which offers no locking, and it is documented in the API.

\subsection{Integrity checks}

Every temperature rs1wire returns, from individual and bulk reads alike, comes from the sensor's `w1\_slave` file.
Unlike `temperature`, which holds only the final value, `w1\_slave` includes the nine raw scratchpad bytes and the kernel's CRC verdict, which makes the following checks possible. w1-therm-api, by contrast, reads bulk results from `temperature` and has nothing to check them against.

When the kernel's own read fails (a bus error, a CRC failure while fetching a bulk result, or an unresponsive sensor), it returns an empty file rather than an error code. rs1wire reports this as `ReadFailed`, or as `ConversionInProgress` if another process is mid-conversion.
Non-empty content is parsed strictly, and anything unexpected is a `Parse` error rather than a panic.
The second line's bytes belong to the last scratchpad that passed CRC, not necessarily the current one, so they are checked only for shape.

rs1wire then recomputes the Dallas/Maxim CRC-8 over bytes 0--7 instead of trusting the kernel.
A mismatch with byte 8, a kernel `NO`, or a kernel CRC that differs from the recomputed one is reported as `CrcMismatch`, so the two calculations can never disagree silently.
An all-zero scratchpad passes CRC-8 but means nothing drove the bus, so it is caught first as `ReadFailed`.
The reported temperature is the kernel's `t=` conversion of these CRC-checked bytes; rs1wire verifies the bytes but does not decode the temperature itself.

Finally, the DS18B20 reads 85~$^\circ$C after power-on until its first conversion completes \cite{ds18b20_datasheet}, so an 85~$^\circ$C reading usually means lost power or an early read, yet is indistinguishable from a genuine one.
By default (`PowerOnResetPolicy::Reject`) rs1wire returns `PowerOnReset`, and its documentation states that this discards genuine 85~$^\circ$C readings; applications that need them can opt in with `PowerOnResetPolicy::Accept`. w1-therm-api makes the same trade-off silently, returning `None`.

\subsection{Parser}

All parsing of kernel output lives in pure functions with no I/O, which keeps it independently testable.
The parser accepts only the exact format the kernel prints: two lines, exactly nine two-digit hex bytes, a `YES` or `NO` verdict, and plain decimal integers.
Anything else, including `+` signs, overflowing values, extra lines, or wrong byte counts, is returned as a `Parse` error carrying a truncated copy of the offending input, so malformed sysfs content can never cause a panic.

\subsection{Correctness testing}

Because the sysfs root is configurable, the 46 unit tests run against fixture directory trees instead of hardware.
They cover discovery across multiple buses, empty buses, and foreign device families; every CRC and read-failure path; the power-on reset policy; each bulk-read refusal; and configuration reads and writes.
A `compile\_fail` doctest confirms that a consumed `BulkConversion` cannot be read again.
Fixtures are plain files, however, so they cannot model the kernel clearing a bulk result when it is read.
That behavior is checked on hardware by `examples/smoke.rs`, and the error rate of every method is also recorded during benchmark runs.

The methods are chosen in pairs so that each comparison changes as little as possible. 
Comparing w1-therm-api's sequential and bulk methods isolates the effect of bulk conversion within a single codebase, while comparing w1thermsensor's sequential reads against either bulk method shows the same effect against the de facto standard library. 
With the architecture held fixed, w1-therm-api-bulk against rs1wire-bulk isolates the language and library effect, and the three sequential methods compare per-call overhead across libraries when every read pays a full conversion. 
If the optional asynchronous w1thermsensor method is run, comparing it with bulk reads tests whether concurrency can close the gap; the bus mutex described in Section~\ref{sec:background} predicts that it cannot on an externally powered bus.

Each method is measured at fixed sensor counts of $N = 1, 2, 5,$ and $10$, using the first $N$ sensors by ROM ID in both harnesses. 
Within each trial, every (method, $N$) cell runs in a seeded random order, and the seed and actual run order are recorded so that slow drift is spread across methods rather than aligned with one. 
One unrecorded warmup trial precedes the recorded ones, and `run\_all.sh` alternates harness blocks in the order Python, Rust, Rust, Python, with 15 trials per block (30 per library). 
Since a bulk trigger converts every sensor on the bus, any results left unread after a bulk cell are drained untimed, and `therm\_bulk\_read` is checked before every cell, with any leftover result flagged in the output. 
With the full bus present, the kernel's periodic bus search is disabled for the run and restored on exit, so a search cycle cannot hold the bus mutex mid-trial.

The following metrics are collected during each trial run:
\begin{itemize}
\item \textbf{Wall-clock time:} measured with `perf\_counter` in Python and `Instant` in Rust.
\item \textbf{CPU time:} total process CPU time from `process\_time` (Python) and `CLOCK\_PROCESS\_CPUTIME\_ID` (Rust), split into user and system time with `getrusage`. The split is tick-sampled, so it is approximate. w1-therm-api's 5~ms polling loop counts toward its CPU time.
\item \textbf{Phase timings:} for bulk methods, the trigger, wait, and readout phases are timed separately where possible. Because the kernel's trigger write is synchronous, w1-therm-api's trigger phase contains the whole conversion and its wait phase is near zero; rs1wire has no separate wait phase and leaves it empty.
\item \textbf{Read outcomes:} the number of successful and failed reads, and the error type of each failure.
\end{itemize}
